# PeakLog 全项目代码审查需求

## 目标

- 对 `PeakLog` iOS 客户端、Live Activity 扩展、测试与 `backend/supabase` 后端做生产级代码审查。
- 找出可验证的架构缺陷、逻辑 Bug、类型安全、并发、数据一致性、安全、性能、可测试性与 UX 流程问题。
- 将确认存在且未重复的问题逐项创建到 `Paikchu/PeakLog` GitHub Issues。

## 审查基线

- Git 基线：`main` / `eece9ed163ab9428902b37233984a49914b2b94d`，与 `origin/main` 一致。
- GitHub 仓库：`Paikchu/PeakLog`。
- 本地工作区存在未提交改动；这些文件仅用于识别潜在冲突，不作为远端 Issue 的确认依据。
- 历史审查报告 `docs/logs/code-review-20260708.md` 只作为线索。每条问题必须用当前代码重新验证，不直接搬运。

## 范围

- iOS：应用入口、SwiftUI Views、ViewModels、Services、Models、Cloud Sync、Auth、Live Activity、App Intents、本地持久化。
- Supabase：迁移顺序与可重放性、表约束、索引、RLS、RPC、触发器、Cron、Edge Functions、密钥边界、跨用户隔离、客户端与数据库契约。
- UX：认证、首次同步、计划生成与重排、训练记录、历史、个人资料、离线/失败/空状态、无障碍与破坏性操作。
- 质量：Swift 与后端测试、构建、静态检查、重复/失效代码、文档与实现漂移。

## Issue 准入标准

- 有明确代码位置或数据库对象，并能说明触发条件与用户/数据影响。
- 能通过代码路径、测试、构建、SQL 检查或运行时行为形成证据。
- 与当前开放 Issue 不重复；重复项只补充证据，不新建 Issue。
- 一个 Issue 聚焦一个可独立修复的根因；同源问题可合并。
- 不把纯偏好、无影响的风格意见或未经验证的猜测发布为 Bug。

## 优先级

- `P0`：安全边界失效、跨用户数据访问、不可恢复的数据损坏或核心流程完全不可用。
- `P1`：高概率数据丢失/错误、认证或同步失败、主流程阻断、严重崩溃。
- `P2`：功能错误、重要 UX 障碍、并发/性能风险、缺失关键错误处理。
- `P3`：低频边界、可维护性、测试缺口、无障碍或轻量性能问题。

## 每个 GitHub Issue 必须包含

- 优先级与问题类型。
- 影响范围和用户后果。
- 证据、文件/符号/迁移位置。
- 触发条件或复现步骤。
- 期望行为与实际行为。
- 根因分析。
- 修复方向与验收标准。
- 相关测试建议；涉及后端时写明 RLS/迁移回归要求。

## 验收

- 当前 `main` 的 iOS 与 Supabase 代码均被覆盖，不只审查最近一次提交。
- 执行可用的 Swift、Node/Deno、Supabase 静态或本地验证，并记录无法执行的外部依赖。
- GitHub 开放 Issue 已去重。
- 所有发布的问题都有优先级、可定位证据、复现/触发条件、修复建议与验收标准。
- 交付 Issue 链接清单，并在 `docs/logs/` 保存本轮审查结果与验证记录。

## 非目标

- 本轮不修改产品代码、不执行数据库写入、不部署 Edge Function。
- 不关闭或改写既有 Issue，除非发现完全重复且用户另行授权。
- 不把本地未提交代码发布到远端。
